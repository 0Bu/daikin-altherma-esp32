# Domain-audit adjudication ledger — tools/domain/catalog_audit.cpp
#
# One finding key per line suppresses that ONE finding (never a whole check). Suppressed findings
# stay printed under "suppressed by …" — an entry here is an adjudication ON RECORD, not a delete.
# Copy the `key:` line the audit prints for the finding you are adjudicating.
#
# Two kinds of entry, and the difference matters:
#
#   ADJUDICATED   The deviation is CORRECT for this model. docs/REGISTERS.md:196-200 is explicit
#                 that the §5 table is a representative model and that families differ — so a real
#                 difference is expected and permanent. Needs evidence: a live capture, or a
#                 documented model fact. Never "it looked fine to me".
#
#   KNOWN-DEFECT  The finding is REAL and not yet fixed. Temporary. Carries the tracking issue and
#                 must be deleted in the PR that fixes it — a KNOWN-DEFECT entry that outlives its
#                 fix silences the guard that would catch the fix regressing.
#
# NEVER add an entry to make a NEW finding go away. A finding on code the PR touches is the gate
# doing its job; adjudicating it away is how -971.5 °C shipped in the first place. If a finding is
# wrong because the AUDIT is wrong, fix the audit — that is a bug in the check, not a fact about
# the catalog. (Converter ids that decode identically at a given width — conv 101 vs 152 on a
# 1-byte field — are already proven equivalent by execution and never reach this file.)
#
# ── KNOWN-DEFECT: pre-existing on main @ a5629b5, found by this audit's first run (2026-07-16) ──
#
# These are the audit's own first catch: four real decode defects the 2026-07-16 manual review did
# NOT find, all still live. They are ledgered — not fixed — because fixing them is a separate,
# evidence-gathering change (per issue #37's rule: a genuinely different model layout cannot be
# excluded from the catalog alone), and because a gate must land clean to be usable at all.
#
# (1) 0x61+13 "Ext. indoor ambient sensor (R6T)" — size-2 field starting one byte early.
#     Spec (docs/REGISTERS.md:404) puts R6T at offset 14; these 4 geo profiles read [13..14] —
#     the HIGH byte of "Indoor ambient temp. (R1T)" [12..13] plus R6T's low byte. R6T is therefore
#     assembled from two unrelated sensors and R1T's own reading is intact but R6T's is fabricated.
#     Straddling overlap is impossible on ANY model regardless of family, so no live capture is
#     needed to call this wrong — only to confirm the intended offset is 14.
OVERLAP:altherma_gshp:0x61:12:indoorambienttempr1t~extindoorambientsensorr6t
OVERLAP:altherma_gshp2:0x61:12:indoorambienttempr1t~extindoorambientsensorr6t
OVERLAP:altherma_egsqh_a_series_10kw_geo2:0x61:12:indoorambienttempr1t~extindoorambientsensorr6t
OVERLAP:altherma_egsah_x_ewsah_x_d_series_6_10kw_geo3:0x61:12:indoorambienttempr1t~extindoorambientsensorr6t
#
# (2) 0x63+13 "BUH output capacity" — whole byte published as a 3-bit field's value.
#     Spec (docs/REGISTERS.md:462) says conv 311 = `byte & 0x07` (backup-heater step 0-7).
#     Every profile carrying this row (derive: `grep -rl '"BUH output capacity"' main/def/ | wc -l`)
#     uses conv 152 = the raw u16/byte, so every bit above bit 2 lands in the reading: a byte of
#     0x85 publishes 133 instead of 5. conv 311 is currently a documented-but-unimplemented stub
#     (main/logic/convert.hpp), so the fix is to implement 311 + repoint these rows, with a host
#     CHECK pinning `0x85 -> 5`.

#     22 sibling profiles type it 1 (°C). This one profile types it -1, so discovery.hpp stamps no
#     unit and no device_class: HA gets a bare number instead of a temperature entity. The value is
#     right; what HA is told it MEANS is not.

# (4) 0x30+11 "Outlet water hex temp. before BUH (DLWB2)" — water temp on the outdoor page.
#     Spec (docs/REGISTERS.md:305) puts the 4-Way Valve at 0x30+11 on this shared outdoor page.
#     This profile reads a 1-byte conv-105 temperature there (and another at +10, inside the
#     "Expansion valve 4" window). A size-1 conv-105 temperature can only ever report 0.0-25.5 °C
